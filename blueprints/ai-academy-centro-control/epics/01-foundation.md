## Conventions that bite in this area

- Relative imports use the `.ts` extension (`./app.ts`), not `.js` and not bare — `tsconfig.json`'s
  `allowImportingTsExtensions` + `rewriteRelativeImportExtensions` makes this resolve identically
  under `tsx` and under `tsc`'s build output. Mixing in a `.js` specifier breaks the standalone
  seed script (`tsx` resolves literally).
- `drizzle-kit` and the `auth` CLI both load `.env` on their own — do not add a `--env-file` flag to
  `pnpm db:generate` / `pnpm db:migrate` / `pnpm auth:generate`, they already read it.
- Express 5's wildcard route syntax is `/api/auth/*splat` (a **named** wildcard), not a bare `*` —
  `app.all("/api/auth/*splat", toNodeHandler(auth))` in E1-T4.
- `better-auth`'s Drizzle adapter needs the **combined** schema object (`{ ...appSchema,
  ...authSchema }`), passed to both `drizzleAdapter(...)` in `auth.ts` and to `drizzle(pool, {
  schema })` in `client.ts`. Passing only `src/db/schema.ts` makes `better-auth` log a "Drizzle
  schema mismatch" error at boot even though the tables exist in Postgres — it's checking the JS
  object, not the database.

Full project rules: `CLAUDE.md`. Area rules: `.claude/rules/db-and-auth.md`,
`.claude/rules/views-and-routes.md`. Both sit in the project root — the builder copied them there
from the bundle's `workspace/` before task one.

## Pitfalls

- **Mounting `toNodeHandler(auth)` after `express.json()`.** better-auth's handler needs the raw
  body for some flows; the working order is auth handler first, then `express.json()` for your own
  routes.
- **Passing `src/db/schema.ts` alone to `drizzleAdapter`.** better-auth validates its *JS* schema
  object independently of what Postgres actually has — pass the merged object every time.
- **Hand-editing `src/db/auth-schema.ts`.** Any manual edit is overwritten the next time
  `pnpm auth:generate` runs, silently.
